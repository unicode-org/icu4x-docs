# Challenges with Scaling i18n
Why traditional monolithic i18n architectures hit a wall

---

# Challenge 1: Quadratic Growth of Locale Data

<div class="two-col-wide-right">
<div>

- Every CLDR release adds **more locales** *and* **deeper coverage** per locale.
- Total locale data grows quadratically:
  <div class="card-accent center" style="margin: 12px 0; font-size: 24px; font-weight: 700;">
    Locales &times; Components
  </div>
- A monolithic data bundle that includes every locale and every component grows by megabytes per release.

</div>
<div class="center">
  <img src="assets/cldr-growth.png" alt="CLDR Growth Chart" style="max-height: 430px; border-radius: 8px; border: 1px solid #cbd5e1;" />
  <div class="muted" style="font-size: 16px;">Each line is one CLDR release: locales ranked by coverage (horizontal) × coverage % (vertical)</div>
</div>
</div>

---

# Challenge 2: Bundling Every Language Doesn't Scale

<div class="two-col-wide-right">
<div>

- **Supporting more languages is essential for users** and digital inclusion—especially for digitally disadvantaged communities.
- However, **statically bundling hundreds or thousands of languages into every app binary doesn't scale**.
- If each language adds ~100 KB, bundling 1,000 languages adds **100 MB** to every user's download.
- **What i18n needs**: Lean static defaults + **dynamic on-demand language packs**.

</div>
<div class="center">
  <img src="assets/language-tail.png" alt="Cumulative installs by number of default languages" style="max-height: 400px; border-radius: 8px; border: 1px solid #cbd5e1;" />
  <div class="muted" style="font-size: 16px;">Past ~70 bundled languages, the extra download size costs more installs than the new languages gain</div>
</div>
</div>

# Challenge 4: New Programming Languages Every Year

<div class="center" style="margin-top: 10px;">
  <img src="assets/pypl-languages.png" alt="PYPL Programming Languages" style="max-height: 360px; border-radius: 8px; border: 1px solid #cbd5e1;" />

- For 25+ years Unicode has maintained **ICU4C** (C/C++) and **ICU4J** (Java)—keeping two separate implementations in sync already requires immense effort.
- Modern ecosystems (**Rust, Dart/Flutter, TypeScript/WASM, Swift, Kotlin, Python, Go**) need first-class, idiomatic i18n APIs without rewriting Unicode & CLDR algorithms from scratch in every language.

---

# Challenge 5: Privacy & On-Device Processing

<div class="card-accent" style="margin-bottom: 14px; font-size: 20px;">
  <strong>i18n libraries process sensitive user data continuously</strong>—we cannot send user data to a central server ("i18n-as-a-service"); everything must run <strong>on-device</strong>:
</div>

<div class="two-col">
<div>

- **Protecting user privacy**: Messages, search queries, contacts, dates, and locale preferences must never leave the device just to format, sort, or break lines.
- **Data-heavy algorithms**: Every scroll, resize, or keystroke segments and measures user text directly in the UI render loop.
- **Low latency & offline resilience**: On-device execution guarantees instant response times and works reliably offline.

</div>
<div class="card" style="font-size: 19.5px; line-height: 1.55;">

**Word & Line Break Points in Japanese User Text:**

Word breaks:

# What Is ICU4X?

<div class="two-col-wide-left" style="margin-top: 18px;">
<div>

- **Portable by Design**
  Runs on all types of devices (`no_std` to cloud) with auto-generated wrappers for C, C++, JavaScript/TypeScript, and Dart via **Diplomat**.

- **Lightweight**
  Modular architecture engineered for compile-time dead-code elimination and fine-grained data slicing (**50–90% smaller footprint** than ICU4C).

- **Secure & Fast**
  Written in memory-safe **Rust** with zero-copy deserialization (`ZeroVec`) and zero heap allocations during formatting (`Writeable`).

</div>

# The `DataProvider` Trait

<div class="two-col">
<div>

- **`DataProvider<M: DataMarker>`** underlies everything ICU4X does with data.
- Each **`DataMarker`** represents an atomic unit of locale data (e.g., `DatetimeNamesMonthGregorianV1`).
- Every formatter constructor with `_unstable` declares its exact required data markers as Rust trait bounds:

</div>
<div>

```rust
// impl<FSet> DateTimeFormatter<FSet>
pub fn try_new_unstable<P>(
    provider: &P,
    prefs: DateTimeFormatterPreferences,
    field_set: FSet,
) -> Result<Self, DateTimeFormatterLoadError>
where
    P: DataProvider<DatetimeNamesMonthGregorianV1>
     + DataProvider<DatetimePatternsDateGregorianV1>
     + DataProvider<DecimalSymbolsV1>
     + /* ... */;
```

</div>
</div>

<div class="card-accent" style="margin-top: 14px;">
  Because the compiler knows <strong>statically</strong> which <code>DataProvider&lt;M&gt;</code> impls are called, unused data markers are automatically dead-code eliminated!
</div>

# Concrete Data Providers & Adapters

<div class="two-col">
<div>

### Concrete Providers
- **Baked (`icu_provider_baked`)**: Compiles CLDR data directly into Rust `const` tables. Zero deserialization cost; linker strips unused markers.
- **Blob (`icu_provider_blob`)**: Platform-independent binary serialization (`postcard`). Load from files, HTTP, or memory (`BufferProvider`).

# Step 1: Generating a Data Pack with `icu4x-datagen`

- Install the `icu4x-datagen` CLI tool (or use the `icu_provider_export` Rust crate in a build script):

```bash
cargo install icu4x-datagen
```

- Generate a dynamic binary blob containing CLDR data for **Chakma (`ccp`)**:

```bash
icu4x-datagen \
  --markers all \
  --locales ccp \
  --format blob \
  --out ccp.blob
```

- This fetches upstream CLDR + ICU export data and serializes `ccp.blob`.

# Step 3: Slimming Data with `--markers-for-bin`

- Wait—how big was `ccp.blob` when we passed `--markers all`?
  - **`5,448,603 bytes` (5.4 MB)**! Because `--markers all` exported collation, display names, units, segmenter dictionaries, and every component in ICU4X.
- Instead of listing markers by hand, point `icu4x-datagen` at our compiled binary (`.exe` or `.wasm`):

```bash
icu4x-datagen \
  --markers-for-bin target/release/tutorial \
  --locales ccp \
  --format blob \
  --overwrite \
  --out ccp.blob
```

<div class="card-accent center" style="margin-top: 14px; font-size: 26px; font-weight: 800;">
  <code>5,448,603 bytes</code> (5.4 MB) &nbsp; ➔ &nbsp; <span style="color: #15803d;"><code>13,711 bytes</code> (13.7 KB)!</span> &nbsp; (99.7% reduction)
</div>

# Step 4: Narrower APIs = Even Smaller Data

- Why is a single locale's date data still **13.7 KB**?
  - `DateTimeFormatter` supports **all calendars** (`en-u-ca-hebrew`, Islamic, Chinese, Japanese, Coptic, Indian…), so `--markers-for-bin` retains month/era names for every calendar!
- If our app only formats **Gregorian** dates, switch to **`FixedCalendarDateTimeFormatter<Gregorian, ...>`**:

```rust
use icu::calendar::Gregorian;
use icu::datetime::FixedCalendarDateTimeFormatter;

let dtf = FixedCalendarDateTimeFormatter::<Gregorian, _>::try_new_with_buffer_provider(
    &provider, locale.into(), YMD::medium()
)?;
println!("{}", dtf.format(&iso_date.to_calendar(Gregorian))); // input must be Gregorian
```

- Re-running `--markers-for-bin` now detects only **5 data markers** (`DatetimeNamesMonthGregorianV1`, `DatetimeNamesYearGregorianV1`, `DatetimePatternsDateGregorianV1`, `DecimalDigitsV1`, `DecimalSymbolsV1`):

<div class="card-accent center" style="margin-top: 10px; font-size: 26px; font-weight: 800;">
  <code>13,711 bytes</code> (13.7 KB) &nbsp; ➔ &nbsp; <span style="color: #15803d;"><code>4,711 bytes</code> (4.7 KB)!</span>
</div>

# New & Improved Calendars (`icu_calendar` 2.2 & 2.3)

<div class="two-col" style="gap: 16px;">
<div class="card">

### **Type-Safe Construction & Arithmetic**
- **Lunisolar Leap Months without Strings**: Construct dates directly with typed `Month` (`Month::new(5)` vs. `Month::leap(5)`) and `YearInput` (`Extended(5786)` or `EraYear("reiwa", 8)`).
- **Flexible Date Construction (`Date::try_from_fields`)**: Build dates from a bag of fields with ECMA-262 Temporal semantics—configurable `Overflow` (`Constrain` vs. `Reject`) and `MissingFieldsStrategy`.
- **Cross-Calendar Date Arithmetic**: Add durations (`try_add_with_options`) and compute differences (`try_until_with_options`) across all 15+ calendars, with **75% faster** year/month diffing.

</div>
<div class="card-accent">

### **Smarter Resolution, Coverage & Footprint**
- **Locale-Aware Calendar Resolution**: `AnyCalendarKind::try_new` now uses likely subtags to infer regional default calendars from language-only locales (e.g., `fa` ➔ Persian, `th` ➔ Buddhist).
- **First-Class Julian Calendar**: Added `Julian` directly to `AnyCalendar` for historical date conversion and formatting.
- **20 KB Smaller Japanese Era Data**: Optimized Japanese era start dates and stopped persisting loaded data inside the `Japanese` calendar struct.

</div>
</div>

# DateTime & Currency Formatting Upgrades

<div class="two-col" style="gap: 16px;">
<div class="card">

### **DateTime (`icu_datetime`)**
- **Date Range Formatting (`DateRangeFormatter`)** <span class="badge-unstable">unstable</span> (+ FFI): Formats intervals (*Oct 20 – 23, 2026*) and automatically collapses to a single date when start == end.
- **Less Ambiguous Yearless Dates** <span class="badge">2.4</span>: Medium/Long `MD` and `MDE` formats now use abbreviated/wide month names (`MMM`/`MMMM`) instead of ambiguous all-numeric patterns.
- **Flexible Day Periods (`B`)**: Localized day period formatting (*"in the morning"*, *"at night"*).
- **Dynamic Field Sets (`DateTimeFieldBag`)** <span class="badge">2.4</span> <span class="badge-unstable">unstable</span>: Runtime UTS #35 skeleton parsing into semantic field sets.

</div>
<div class="card">

### **Currency (`icu_experimental::currency`)** <span class="badge-unstable">unstable</span>
- Supports standard (`$12,345.67`), narrow, long localized names, explicit ISO codes (`USD 12,345.67`), compact (`$12K`), and **Accounting** (`($12,345.67)`) formats.
- **Number-Only Currency (`try_new_no_currency`)**: Applies currency-specific rounding/precision (0 decimals for `JPY`, 2 for `USD`) without printing the currency symbol.
- Respects locale-specific negative sign placement (e.g. `de-CH` formats `-12345.67 CHF` as `CHF-12'345.67`).

</div>
</div>
